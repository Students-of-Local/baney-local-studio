# Local Studio

Native desktop clients for local LLM work. The agent core is [Eukhe](https://github.com/gildrb/eukhe); Local Studio adds native GUIs and the local-LLM fleet.

## Architecture

- Eukhe is the core, like libghostty is Ghostty's: sessions, durable storage, the harness, memory, tools and inference live there. Local Studio never reimplements them.
- The engine runs out of process as the Eukhe daemon (`eukhe --mode daemon`: supervisor + one worker per session), started through `eukhe-client`'s `ProcessLauncher` on Eukhe's socket path. GUIs reach it through the `eukhe-client` crate over the versioned `eukhe.daemon` protocol. A crash in the engine never takes a window down, and every Eukhe frontend can attach to the same session.
- Shared GUI logic lives once, in Rust (`core/`, crate `local-studio-core`): inbox across projects, transcripts, Local Studio state, git, files, terminals, usage, the Local fleet client, settings. Each GUI does only native chrome:
  - `macos/`: Swift + AppKit/SwiftUI, links the core through UniFFI (`kit/` → `LocalStudioKit`), like Ghostty links `GhosttyKit`.
  - `linux/`: Rust + GTK4 + libadwaita, links the core as a crate (own workspace, see `linux/AGENTS.md`).
- Core → GUI: `Studio` methods are fire-and-forget; the core calls `Waker.wake()` and the GUI drains `Studio.tick()` on its main thread into `Update`s.
- `controller/`: the local-LLM controller (Bun, port 18091): engine discovery, fleet gateway, registry launches. The core talks to it over HTTP and can start a bundled copy with its own data root.

## Rules

- Logic needed by both GUIs goes in `core/`; platform behavior (windows, menus, toolbars, notifications) stays in the GUI. Never port core logic into Swift or GTK code.
- Eukhe changes land in the eukhe repo, not as copies or patches here. Both workspaces pin `eukhe-client` and `eukhe-types` to one Eukhe release tag (git dependencies, root `Cargo.toml`); the apps bundle the `eukhe` binary of that same release (`eukhe.nu`: downloaded from the GitHub release and checked against its `SHA256SUMS` into `<target>/eukhe/<tag>/`, or `EUKHE_BIN=<eukhe built from the tag>`). Move both together.
- Verify end to end: build and run the real binaries. No new unit tests.
- Add no code comments.
- Never stop processes, controllers, engines, or GPU jobs this work did not start. Kill only PIDs you spawned.
- Controller: keep native inference requests as passthrough. Never disable CUDA graphs, enforce eager, or set output caps on vLLM/SGLang. New controllers use port 18091 and a separate data root.
- Never run against real user state in checks: isolate with `HOME`, `EUKHE_DAEMON_SOCKET`, `EUKHE_CODING_AGENT_DIR`, `LOCAL_STUDIO_DATA_DIR` under a scratch dir; stop the daemon after (`core` smoke example `--stop <socket>`).
- Checks drive a real model, never a faux one: a local model named by `LOCAL_STUDIO_SMOKE_MODEL=<provider>/<model>` (the gate uses `ollama/fv-smoke-lfm3-1.7b` on abbey1's Ollama), a handful of short prompts per run, one run at a time. Never an Anthropic model through Eukhe: its subscription sign-in is ruled out (Donovan, 2026-11-17) and API keys are paid billing. The core examples write their own scratch `models.json` (that one keyless provider at `LOCAL_STUDIO_SMOKE_BASE_URL`, default `http://127.0.0.1:11434/v1`, with a real context window), `settings.json` and an `auth.json` of `{}`, all mode 0600, and link no credential. On abbey1 claim the shared GPU first (`~/.local/bin/ollama-window wait <minutes> <model> <who>`, then `release <who>`); `scripts/e2e.sh` does this itself. Assert behavior a correct app always shows (a real tool call and its file, the reply arriving, transcript order, usage with real tokens and cost), never model wording. docs/e2e.md has the model choice and the daily timer. `claude_signin_smoke` drives no model at all: it checks that Claude sign-in threads are refused before any model is asked.
- `macos/AGENTS.md` and `linux/AGENTS.md` hold the per-platform build and lint rules.

Its project settings stage requires a Claude Code thread in a project with its own settings to start no CLI until its card is answered, a denied one to run with `--setting-sources user`, again after another thread of the project is allowed, one answer to settle the project's other waiting threads and its linked worktrees, a folder whose `.git` file or link only claims to be such a worktree to be asked about, as is a project under a folder with its own `CLAUDE.md`, Stop to take the card away, and a card left open to come back after a restart with its message; a Codex thread is asked the same way about a project's `.codex`, names every folder up to its git top, and a linked worktree's main checkout, as untrusted when denied (a restart included), together with a folder above the git top that holds a `.codex`, is asked when only that folder or a linked worktree's main checkout holds it, is marked trusted with no question when none does (never the home folder, even as a git repo), is marked trusted by the answer to a Claude Code thread's card on the same project, is not asked there again, and always runs its `codex` in the home folder. - Updater end to end, no model: `cargo run -p local-studio-core --example update_smoke -- <scratch>`. It serves a feed on 127.0.0.1 signed with a throwaway minisign key and requires: a local build never fetches; another channel's feed, an older or equal version, a bad sha256 and four bad signatures (other key, tampered, wrong file, unsigned) are refused with nothing staged; a newer build is downloaded and staged in the data dir; `scripts/install.sh --feed --public-key --prefix` installs it with each verifier present (minisign, OpenSSL 3, python3) and refuses the same four bad downloads leaving nothing installed; the Tauri CLI's own signature verifies (`npx`, skipped without it); apply swaps it in keeping `.previous`, refuses an ad-hoc signed bundle on macOS, and rolls back a build that fails after the swap. On macOS it signs with a scratch identity in a scratch keychain (`HOME` under the scratch) and checks the real keychain list is unchanged. `local-studio update check|download|status|apply [--target <path>] [--no-relaunch]` runs the same steps on the running build's own channel

- Cargo target: give each worktree its own, such as `CARGO_TARGET_DIR=/tmp/ls-target-<branch>`. Other sessions build this repo on the same machine, and a shared target lets their build replace the binary a smoke is about to run (twice: knowledge/field-notes/local-studio/smoke-ran-another-worktree-s-binary-from-a-shared-cargo-target-dir.md). To skip the first full build, clone a warm one on APFS: `cp -c -R /tmp/ls-cargo-target/debug /tmp/ls-target-<branch>/`. Before a smoke, check the binary is yours: `<binary> --version` names your commit and channel. The channel is set with `LOCAL_STUDIO_CHANNEL`, not `LOCAL_STUDIO_BUILD_CHANNEL`
- Local CI, for when GitHub Actions starts no run: `nu scripts/local-ci.nu <pr> --post` from a checkout runs every Linux job in `.github/workflows/ci.yml` on the PR's head, each in a fresh worktree, and posts a `local/<job name>` commit status for each. It runs only the owner's own branches. It needs the zig and nu versions CI pins, on `PATH` or in `~/.local/opt/<tool>-<version>/` (chapel1 has both); without nix it builds the Linux app against the host's GTK libraries and adds the flake's zig.
