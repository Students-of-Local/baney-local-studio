# Plugins from other agents

Decision, 2026-11-22 (Claude, Local Studio lead), after a survey of the Claude Code, Codex, Hermes, Gemini CLI, Cursor, Goose, MCP Registry and Agent Skills systems and the ClawHub malware incident (1,184 malicious skills whose "Prerequisites" told people to paste terminal commands).

Local Studio installs a Claude Code or Codex plugin as it is, from a folder, a git URL or a marketplace, through the same consent sheet, grants and tree hash as its own plugins. Nothing a foreign plugin ships runs unless Local Studio can show it on the sheet and cover it with the hash.

## One format on disk

Local Studio translates at install, never at load. `local-studio plugin install` (and `Studio::install_plugin`) finds a foreign manifest in the fetched copy, writes a `plugin.toml` into that scratch copy, then hashes, scans and installs it exactly as it does a native plugin. So:

- the loader, the scanner, grants and the consent sheet read one format, `plugin.toml`;
- the tree hash covers the generated manifest and any generated launcher, so changing either needs consent again;
- the generated `plugin.toml` starts with `# Generated by Local Studio <version> from <manifest path>. Do not edit; reinstall instead.`

A folder that has its own `plugin.toml` is native, whatever else it holds. Hildegard, which ships both, installs as native.

## Which manifests

| Found (first match wins) | Kind |
| --- | --- |
| `plugin.toml` | native |
| `.claude-plugin/plugin.json` | Claude Code |
| `.codex-plugin/plugin.json`, else a root `plugin.json` with a `name` and at least one of `skills`, `mcpServers` | Codex |
| none, but a `skills/` folder of Agent Skills (`*/SKILL.md`) | skills pack (id from the folder or repo name) |

`gemini-extension.json` is not read: Gemini CLI was replaced in June 2026.

A marketplace is a repository with `.claude-plugin/marketplace.json` (Claude Code) or Codex's marketplace file (at the path Codex's docs give; check them when this is built and cite them here). `local-studio plugin install <git url> --plugin <name>` reads it, resolves that one plugin's source (a relative path in the same repository, or a git URL with an optional `ref` or `sha`), and installs that. A plugin whose source is npm, an archive URL or a `command` source is refused: its bytes can't be fetched and pinned the way git is. Without `--plugin`, install on a marketplace lists its plugins and installs nothing.

## The mapping

| Theirs | Local Studio |
| --- | --- |
| `name` | `id`, folded to lowercase letters, digits and single hyphens; refused if that leaves nothing or collides with an installed plugin from another source |
| `displayName` / `name` | `name` |
| `version` | `version`; absent or not semver gives `0.0.0` (the tree hash still pins the bytes) |
| `description` | `description`; absent gives `<name>, a <Claude Code or Codex> plugin` |
| `skills/` (or the manifest's `skills` path or paths inside the plugin) | `skills` (Agent Skills `SKILL.md` is the format Local Studio reads already) |
| `commands/*.md` (Claude Code) | one `[[commands]]` each, name from the file stem, description from its frontmatter, the file as a prompt |
| one MCP server (`.mcp.json`, `mcp.json` or `mcpServers` in the manifest) | `[mcp]` and the `mcp-server` capability, only as below |
| hooks, agents, LSP servers, monitors, output styles, `bin/`, apps, `userConfig` | not used; each is listed on the sheet under "Not used by Local Studio" |

### Prompts from Claude Code commands

A Claude Code command can run shell lines when it expands (lines with an exclamation mark before a backtick span) and can name `allowed-tools`. Local Studio runs neither: the prompt is text. Each such line is a finding on the sheet ("runs `<line>` in Claude Code; Local Studio sends it as text"), so the person sees what the author meant to run. `$ARGUMENTS` and `$1`..`$9` map to Local Studio's own argument placeholder if it has one; otherwise they stay as text and the command's description says it takes no arguments here.

### MCP servers

The server is set up only when its code is inside the plugin, so the hash covers it:

- `command` is a path inside the plugin after `${CLAUDE_PLUGIN_ROOT}`, `${PLUGIN_ROOT}` or `./` is resolved: used as it is.
- `command` is `node`, `python3`, `python`, `bun`, `deno` or `uv`, and the first argument that names a file resolves inside the plugin (for `uv`: `run --project <dir inside the plugin>` or a script inside it): Local Studio writes a launcher, `.local-studio/mcp` (POSIX sh; `.local-studio/mcp.cmd` on Windows), that `exec`s the interpreter found on `PATH` at start with the original arguments, and points `[mcp] command` at it. The sheet's scope line shows the original command and arguments.
- Anything else is not set up, and the sheet says why: `npx`, `uvx`, `pipx run`, `bunx`, `docker`, an absolute path outside the plugin, or a remote server (`url`, `type: http` or `sse`) runs or reaches code the hash can't cover. More than one server: none is set up in this version, and each is listed.

`env` values pass through under the existing rules (a value that names a host variable keeps the plugin from asking questions; `LOCAL_STUDIO_CALLER` and `LOCAL_STUDIO_CALLER_NAME` are refused). `${CLAUDE_PLUGIN_DATA}` resolves to `<data dir>/plugin-data/<id>`, outside the plugin folder, so state never changes the hash.

A translated plugin asks for no capability beyond `mcp-server`. It can't ask questions (`ask-user`) or get a sensitive capability: those are Local Studio's own manifest fields, and a plugin that needs them ships a `plugin.toml`.

## What the person sees

The consent sheet for a translated plugin adds, above the rows:

- the kind and the manifest it came from ("A Claude Code plugin, translated by Local Studio"), and the source with its commit, as for any git install;
- "Not used by Local Studio": every hook, agent, LSP server, monitor, server that was not set up, and `bin/` file, by name, each with the reason;
- the findings, which for every plugin, native or not, now also include the text findings below.

Install stays off until the person opens the findings, as it does today for executables.

## Text findings, for every plugin

The ClawHub incident ran through instructions, not code: a skill told the person, or the agent, to paste a command. So the scan reads every `SKILL.md`, prompt and command file (and any `*.md` a skill folder holds) and lists, with the file and line:

- a download piped or fed to a shell or interpreter: `curl` or `wget` into `sh`, `bash`, `zsh`, `python`, `node`, `iex`; `bash <(curl ...)`; `irm ... | iex`;
- decoding into a shell: `base64 -d`, `xxd -r`, `openssl enc -d` piped into a shell;
- `powershell -enc` / `-EncodedCommand`; `osascript -e` with `do shell script`;
- reads of secrets: `~/.ssh`, `id_rsa`, `id_ed25519`, `.env`, `~/.aws/credentials`, keychain or `security find-generic-password`, browser profile folders, wallet folders;
- sending a file to a host: `curl -F`/`--data @`/`-T` with a file, `nc` to a host, `scp`/`rsync` to a host.

A finding is not a verdict: an installer line such as `curl -LsSf https://astral.sh/uv/install.sh | sh` is common and legitimate. The sheet shows the exact line so the person decides. These are findings, not blocks, in this version; a non-overridable block list needs a curated source of known-bad content, which Local Studio does not have yet.

## Updates

A translated plugin updates like any git plugin: same source, new tree. The update's sheet lists only new capabilities, as today, plus any newly not-used item and any new text finding compared with the installed tree, so a plugin that adds a hook or a `curl | sh` line in an update is shown again.

## Done check

- Unit tests over fixture plugins in `core/src/plugins/tests.rs` (or a new `compat` test module): a Claude Code plugin with skills, two commands (one with a shell line), one MCP server via `node ${CLAUDE_PLUGIN_ROOT}/server.js`, a hook and an agent; a Codex plugin with skills and `uv run --project`; a plugin with an `npx` server; a remote `url` server; two servers; a marketplace with a relative-path plugin and one npm-sourced plugin; a bare skills pack; a native plugin that also has `.claude-plugin/` (stays native). Each asserts the generated `plugin.toml`, the launcher, the not-used list, the findings, and that `load` of the installed copy succeeds.
- Text findings: each pattern above found once in a fixture, and an ordinary skill gives none.
- An install of Hildegard's own `.claude-plugin` folder layout from a scratch copy without its `plugin.toml` translates and validates.
- `cargo fmt`, `cargo clippy --workspace --all-targets -D warnings`, `cargo test -p local-studio-core` pass on Linux.
