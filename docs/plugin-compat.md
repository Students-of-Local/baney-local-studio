# Plugins from other agents

Decision, 2026-11-22 (Claude, Local Studio lead), after a survey of the Claude Code, Codex, Hermes, Gemini CLI, Cursor, Goose, MCP Registry and Agent Skills systems and the ClawHub malware incident (1,184 malicious skills whose "Prerequisites" told people to paste terminal commands).

Local Studio installs a Claude Code or Codex plugin as it is, from a folder, a git URL or a marketplace, through the same consent sheet, grants and tree hash as its own plugins. Nothing a foreign plugin ships runs unless Local Studio can show it on the sheet and cover it with the hash.

## One format on disk

Local Studio translates at install, never at load. `local-studio plugin install` (and `Studio::install_plugin`) finds a foreign manifest in the fetched copy, writes a `plugin.toml` into that scratch copy, then hashes, scans and installs it exactly as it does a native plugin. So:

- the loader, the scanner, grants and the consent sheet read one format, `plugin.toml`;
- the tree hash covers the generated manifest and any generated launcher, so changing either needs consent again;
- the generated `plugin.toml` starts with `# Generated by Local Studio <version> from <manifest path>. Do not edit; reinstall instead.`

A folder that has its own `plugin.toml` is native, whatever else it holds. Hildegard, which ships both, installs as native.

The plugin never decides whether it counts as translated. That header is only a note for people. When install runs the translation, it writes `translated: true` into that plugin's entry in `origins.json`, in the plugins folder, which no plugin writes. Local Studio treats an installed plugin as translated only when that record says so and the folder still holds exactly that translation: the `plugin.toml` it would write from the folder today (the version in the header aside) and the same launcher. Otherwise the plugin is native, so a native plugin that copies the header and ships a `.claude-plugin/plugin.json` gets a native sheet.

## Which manifests

| Found (first match wins) | Kind |
| --- | --- |
| `plugin.toml` | native |
| `.claude-plugin/plugin.json` | Claude Code |
| a root `plugin.json` with a `name` and an Agent Plugins `$schema`, a `skills`, `mcpServers` or `extensions` key, a `skills/` folder or an `mcp.json` | Codex (the portable manifest) |
| `.codex-plugin/plugin.json` | Codex (the compatibility manifest) |
| none, but a `skills/` folder of Agent Skills (`*/SKILL.md`) | skills pack (id from the folder or repo name) |

Sources for these paths, read 2026-11-22: Claude Code's plugin manifest is `.claude-plugin/plugin.json`, and its components (`skills/`, `commands/`, `agents/`, `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `monitors/monitors.json`, `bin/` and the rest) are given in the plugins reference, https://code.claude.com/docs/en/plugins-reference. Codex's build guide, https://developers.openai.com/plugins/build/plugins (linked from https://developers.openai.com/codex/plugins), makes the root `plugin.json` (the Agent Plugins schema, with OpenAI settings under `extensions.com.openai`) the canonical manifest and reads `.codex-plugin/plugin.json` as the fallback, which is why the root file comes first here.

`gemini-extension.json` is not read: Gemini CLI was replaced in June 2026.

A marketplace is a folder or repository with `.claude-plugin/marketplace.json` (Claude Code, https://code.claude.com/docs/en/plugins/marketplace-reference) or `.agents/plugins/marketplace.json` (Codex, https://developers.openai.com/plugins/build/plugins; Codex also reads the Claude Code file). `local-studio plugin install <source> --plugin <name>` takes a source the way `plugin install` already does (a folder, or a git URL with `@<commit>`), reads the marketplace, resolves that one plugin's source and installs that. Sources Local Studio follows:

- a relative path (`./plugins/x`, or a bare name under `metadata.pluginRoot`), or Codex's `{"source": "local", "path": ...}`: the same folder or the same commit of the same repository. A path with `..`, a backslash or a symlink that leaves the marketplace is refused, through the same `inside()` check the loader uses;
- `github`, `url` and `git-subdir`: the git URL at `sha` when given, else the commit that `ref` names now, else the commit the app's channel resolves to. The install records that commit, so it is pinned like any other git install.

A plugin whose source is npm, an archive URL or a `command` source is refused: its bytes can't be fetched and pinned the way git is. Without `--plugin`, install on a marketplace lists its plugins and installs nothing. A folder that holds a plugin manifest is a plugin even when it also holds a marketplace file (Hildegard's repository has both, and its marketplace lists itself as `./`); the marketplace is read only when the root has no plugin or with `--plugin`. A Claude Code marketplace entry that has no `plugin.json` of its own (the entry is the manifest) is not supported, unless the folder is a bare skills pack.

## The mapping

| Theirs | Local Studio |
| --- | --- |
| `name` | `id`, folded to lowercase letters, digits and single hyphens; refused if that leaves nothing or collides with an installed plugin from another source |
| `displayName` (Codex: `interface.displayName`) / `name` | `name` |
| `version` | `version`; absent or not semver gives `0.0.0` (the tree hash still pins the bytes) |
| `description` | `description`; absent gives `<name>, a <Claude Code or Codex> plugin` |
| `skills/` (or the manifest's `skills` path or paths inside the plugin) | `skills` (Agent Skills `SKILL.md` is the format Local Studio reads already). Local Studio reads one skills folder: `skills/` when present, else the first listed path; any other is listed as not used. The loader's rule still holds: every subfolder of that folder must be a skill |
| `commands/*.md` (Claude Code), or the manifest's `commands` path, paths or name map with `source` | one `[[commands]]` each, name from the file stem (or the map key), description from its frontmatter (else its first line), the file as a prompt. A command in a subfolder of `commands/`, one whose text is inline in the manifest, one whose name Local Studio doesn't take and a second one with the same name are listed as not used |
| one MCP server (`.mcp.json`, `mcp.json` or `mcpServers` in the manifest; a later one with the same name replaces an earlier one) | `[mcp]` and the `mcp-server` capability, only as below |
| hooks, agents, LSP servers, monitors, output styles, workflows, themes, `bin/`, apps, `userConfig`, channels, plugin dependencies, `.mcpb` bundles | not used; each is listed on the sheet under "Not used by Local Studio" |

### Prompts from Claude Code commands

A Claude Code command can run shell lines when it expands (lines with an exclamation mark before a backtick span) and can name `allowed-tools`. Local Studio runs neither: the prompt is text, and `allowed-tools` is ignored. Each such line is a finding on the sheet ("runs `<line>` in Claude Code; Local Studio sends it as text"), so the person sees what the author meant to run. `$ARGUMENTS`, `$1`..`$9` and `$@` pass through unchanged: Local Studio's prompt expansion (`substitute_args` in `core/src/skills.rs`) already fills the same placeholders.

### MCP servers

The server is set up only when its code is inside the plugin, so the hash covers it, and only in a form that fetches nothing at start that the hash doesn't cover:

- `command` is a path inside the plugin after `${CLAUDE_PLUGIN_ROOT}`, `${PLUGIN_ROOT}` or `./` is resolved. An executable file under `bin/` is used as it is (install already refuses executables outside `bin/`). Any other file whose `#!` line names `node`, `python3`, `python`, `bun` or `deno` is started through that interpreter, as in the next point. Anything else is not set up.
- `command` is `node`, `python3`, `python`, `bun`, `deno` or `uv`, and the file it runs resolves inside the plugin: Local Studio writes a launcher, `.local-studio/mcp` (POSIX sh; `.local-studio/mcp.cmd` on Windows), that `exec`s the interpreter found on `PATH` at start, and points `[mcp] command` at it. The sheet's scope line names the launcher and, beside it, the original command and arguments with the variables the launcher exports. To keep the start offline:
  - `node`, `python3`, `python`: the first argument must be the file; interpreter flags before it are not passed.
  - `bun`: the same, and the launcher adds `--no-install`, so bun never installs a missing package.
  - `deno`: only `deno run`, only `--allow-*`, `-A` and `-q` before the file, and the launcher adds `--no-remote --no-npm`.
  - `uv`: only `uv run`, with `--project` or `--directory` inside the plugin and `--locked`, `--frozen`, `--no-dev`, `--offline`, `--no-sync` or `-q`; the project folder must hold a `uv.lock`, and the launcher adds `--locked` (unless `--frozen`) and `--no-python-downloads`. uv may still install the locked packages into its cache on first start; the lock file, which the hash covers, pins exactly which.
- Anything else is not set up, and the sheet says why: `npx`, `uvx`, `bunx`, `pnpx`, `pnpm`, `yarn`, `pipx`, `docker`, `podman`, any other program from `PATH`, an absolute path, a path with `..` or a symlink that leaves the plugin, a `cwd` other than the plugin root, or a remote server (`url`, `type: http` or `sse`) runs or reaches code the hash can't cover. More than one server: none is set up in this version, and each is listed.

The launcher is the one executable outside `bin/` that install accepts, and only at those two paths. Every other file outside `bin/` loses its executable bit in the translated copy (Claude Code hook scripts are often executable, and they never run here). A `.local-studio` folder the plugin ships is replaced.

`env` follows the existing `[mcp] env` rule, which takes host variable names: a value `${VAR}` becomes the host variable `LOCAL_STUDIO_PLUGIN_<ID>__VAR`, so the person sets it outside the plugin. Other values (text, `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`) are exported by the launcher. A name that is not capitals, digits and `_`, and `LOCAL_STUDIO_CALLER` and `LOCAL_STUDIO_CALLER_NAME`, are refused. So are the variables that change which program runs or what code it loads, whatever their value: `PATH`, `LD_*`, `DYLD_*`, `NODE_OPTIONS`, `NODE_PATH`, `PYTHONPATH`, `PYTHONHOME`, `PYTHONSTARTUP`, `PYTHONUSERBASE`, `BUN_*`, `DENO_*`, `UV_*`, `PERL5LIB`, `RUBYOPT`, `RUBYLIB`, `JAVA_TOOL_OPTIONS`, `BASH_ENV` and `ENV`. With any of these the server is not set up, and the sheet lists it under "Not used by Local Studio" with the variable it sets. The sheet's scope line shows every variable the launcher exports, as `KEY=value` before the original command. The launcher resolves `${CLAUDE_PLUGIN_DATA}` when it starts, to `<data dir>/plugin-data/<id>` (two folders up from the plugin), outside the plugin folder, so state never changes the hash and the hash doesn't depend on where the data dir is.

A translated plugin asks for no capability beyond `mcp-server`. It can't ask questions (`ask-user`) or get a sensitive capability: those are Local Studio's own manifest fields, and a plugin that needs them ships a `plugin.toml`.

## What the person sees

The consent sheet for a translated plugin adds, above the rows:

- the kind and the manifest it came from ("A Claude Code plugin, translated by Local Studio from .claude-plugin/plugin.json"), and the source with its commit, as for any git install;
- "Not used by Local Studio": every hook, agent, LSP server, monitor, server that was not set up, and `bin/` file, by name, each with the reason. It never names a file the server runs;
- the findings, which for every plugin, native or not, now also include the text findings below.

The `mcp-server` row's scope line always names the command that runs, from `[mcp]`, as a path inside the plugin with its arguments: `.local-studio/mcp` for a launcher, `bin/server` for a native server. For a translated plugin the original declaration follows it, never instead of it, with every variable the launcher exports: "Starts .local-studio/mcp (from .mcp.json: MODE=fast node ${CLAUDE_PLUGIN_ROOT}/server.js) when a thread uses it."

On the wire these are two optional fields of `ConsentRequest`: `translated` (that first line, absent for a native plugin) and `notUsed` (the list). The command lines and text findings go into the existing `findings` list, after the executables, so the existing gate covers them: Install stays off until the person opens the findings, as it does today for executables. A sheet opens for every translated install, and for any install with text findings, even when the plugin asks for no capability.

`local-studio plugin install`, `validate` and `list` print the same first line and the not-used list; install also prints the findings.

## Text findings, for every plugin

The ClawHub incident ran through instructions, not code: a skill told the person, or the agent, to paste a command. So the scan reads every `SKILL.md`, prompt and command file (and any `*.md` a skill folder holds) and lists, with the file and line, the lines below.

The loader and the scan read these files through one shared rule, so the scan covers exactly what the agent gets. A file that is a symlink is read only when it resolves to a regular file inside the plugin, at most 10 MB; the scan then reads that target's text and names both ("skills/setup/SKILL.md -> skills/setup/notes.txt"). A symlink that leaves the plugin or points nowhere is a finding of its own, and the loader skips that skill, prompt or command. A symlinked folder inside a skill folder is followed when it stays inside the plugin.

The patterns:

- a download piped or fed to a shell or interpreter: `curl` or `wget` into `sh`, `bash`, `zsh`, `python`, `node`, `iex`; `bash <(curl ...)`; `irm ... | iex`;
- decoding into a shell: `base64 -d`, `xxd -r`, `openssl enc -d` piped into a shell;
- `powershell -enc` / `-EncodedCommand`; `osascript -e` with `do shell script`;
- reads of secrets: `~/.ssh`, `id_rsa`, `id_ed25519`, `.env` as a word, `~/.aws/credentials`, `security find-generic-password`, `find-internet-password` or `dump-keychain` and keychain files, browser profile folders, wallet folders;
- sending a file to a host: `curl -F`/`--data @`/`-T` with a file, `nc` to a host, `scp`/`rsync` to a host.

A finding is not a verdict: an installer line such as `curl -LsSf https://astral.sh/uv/install.sh | sh` is common and legitimate. The sheet shows the exact line so the person decides. These are findings, not blocks, in this version; a non-overridable block list needs a curated source of known-bad content, which Local Studio does not have yet.

## Updates

A translated plugin updates like any git plugin: same source, new tree. The update's sheet lists only new capabilities, as today, plus any newly not-used item and any new text finding compared with the installed tree (matched by file and line text, not line number), so a plugin that adds a hook or a `curl | sh` line in an update is shown again. An update with none of these installs without a sheet.

Settings, Plugins checks for updates without installing; for a translated plugin it shows no capability list there, because the list exists only once the copy is translated. The sheet at install shows it.

- Unit tests over fixture plugins in `core/src/plugins/tests/compat.rs`: a Claude Code plugin with skills, two commands (one with a shell line), one MCP server via `node ${CLAUDE_PLUGIN_ROOT}/server.js`, a hook and an agent; a Codex plugin with skills and `uv run --project`; a plugin with an `npx` server; a remote `url` server; two servers; a marketplace with a relative-path plugin and one npm-sourced plugin; a bare skills pack; a native plugin that also has `.claude-plugin/` (stays native). Each asserts the generated `plugin.toml`, the launcher, the not-used list, the findings, and that `load` of the installed copy succeeds.
- Text findings: each pattern above found once in a fixture, and an ordinary skill gives none.
- An install of Hildegard's own `.claude-plugin` folder layout from a scratch copy without its `plugin.toml` translates and validates.
- `cargo fmt`, `cargo clippy --workspace --all-targets -D warnings`, `cargo test -p local-studio-core` pass on Linux.
